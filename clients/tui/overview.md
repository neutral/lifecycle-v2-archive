# Foundation Founder TUI

The OpenTUI application owns presentation, terminal layout, editor behavior,
and the stable Founder journey:

`Setup → Frame → Admit → Work → Resolve → Prove → Close`.

It owns no Delivery Process state, state authority path, or independent effect
route. Repository and Delivery facts come from canonical v10 CLI read models.
The persistent tabs are Inbox, Now, Frame, Next Pass, Boundary, Candidate,
Decision, Evidence, Attempt, Journal, Control, and Exact; Candidate is the
noncanonical working lane.

Frame is a multiline text area for one complete fresh reconnaissance brief. It
delegates `delivery.prepare` to the canonical CLI. Each submission is
fresh and creates one new Delivery; previous input, plans, Candidate bytes,
Attempt View facts, and Journal context are never implicit provider input.
Frame is available before a Delivery identity exists. Inbox selects one exact
Delivery rather than an ambient newest result.

Next Pass is a fresh multiline composer over only the reducer-eligible members
of continue, evaluate, revise, and reaffirm. It delegates the selected operation
through the canonical CLI with the reviewed read generation. A refusal
preserves input; a coherent successor clears it. Every pass receives a fresh
Brief, Investment, Projection, and Attempt.

One selected Delivery View supplies coherent Now, Boundary, Candidate,
Decision Readiness, Evidence, Attempt, Journal, Control, and Exact sections.
The runtime also owns the bounded Candidate difference and durable-generation
watch. The TUI does not join cross-generation status, open SQLite, invoke Git,
interpret live support, or construct a parallel result, assessment, or Process
journal view.
Execution Cells remain subordinate Runtime mechanics. The TUI has no Cell,
container, backend, allocation, retirement, reclamation, retry, or pipeline
journey. An inspected Attempt View may carry stable Candidate Carrier,
execution-selection, output, Containment, and Retirement facts, but those facts
remain subordinate evidence beneath the owning Delivery operation and do not
create TUI navigation, controls, or selectable identities.

The tab row is fixed below the header. The footer always reserves one bottom
row, including transient `REFRESHING`, so refresh never shifts the layout.
Admission, acceptance, no-ship, and recovery remain print-only CLI handoffs.
The TUI neither reads authority secrets nor executes those operations.
