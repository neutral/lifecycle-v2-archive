# Target codebase layout

## Purpose

Use this page to create the target repo storage shape for Lifecycle.

This page owns layout and placement. Use [install-procedure.md](install-procedure.md)
for install steps, [first-run.md](first-run.md) for the first invocation, and
[verification.md](verification.md) for setup checks.

## Root Shape

A target codebase has two Lifecycle roots:

```text
records/     Context, Intent, Assurance, Blueprint, and persisted Control records
.lifecycle/  local methodology, discipline, scratch, and temporary support
```

`records/` is versioned with the target codebase. `.lifecycle/` is gitignored
local support.

## Local Lifecycle Layout

Create this local folder at the target codebase root:

```text
.lifecycle/
  methodology/
    local-support/
    semantic-authority/
    disciplines/
    control-records/
    states/
    checks/
    responses/
  disciplines/
    catalog.md
    package-info/
    bindings/
    surfaces/
    cache/
    discipline.lock
  methodology.lock
  usage/               installed operating docs; tools/ covers the lt CLI
  scratch/
  work-traces/
  stop-work-requests/
  tooling/             optional generated tooling support
```

`.lifecycle/methodology/` stores installed methodology for the target codebase.

`.lifecycle/disciplines/` stores installed package info, generated
surface content, discipline bindings, the discipline catalog, local
cache, and discipline lock metadata. It is ignored local support, not
product meaning or process state.

`.lifecycle/methodology.lock` records which Lifecycle source packages were
installed.

`.lifecycle/scratch/` stores temporary reasoning, local notes, and work support
that should not become committed product records or persisted Control records.

`.lifecycle/work-traces/` stores optional local work traces for active runs.
`.lifecycle/stop-work-requests/` stores external interruption requests for
active runs. Both are gitignored local support.

`.lifecycle/tooling/` stores optional generated tooling support when tool
assistance is enabled. It can contain generated support, caches, findings,
proof receipts, prepared material, local tool config, and support lock
metadata. It is ignored local support, not product meaning or process state.
Core Lifecycle does not require this folder.

When generated by setup, `.lifecycle/tooling/support/` contains source-owned
contract copies and `contract-registry.json`. `.lifecycle/tooling/tooling.lock.json`
records source contract hashes and freshness inputs.

## Placement Rule

Use this placement rule in a target codebase:

```text
product meaning -> records/<semantic authority surface>/, except Description
Description meaning -> code-adjacent **/_*.desc.md files
process state -> records/control/
Context-pass state -> records/control/clarity/ while Clarity is active
product judgment -> records/control/delivery/work-boundaries/ while Delivery is active
discipline material -> .lifecycle/disciplines/
temporary reasoning -> .lifecycle/scratch/
work trace support -> .lifecycle/work-traces/
stop-work request support -> .lifecycle/stop-work-requests/
generated tooling support -> .lifecycle/tooling/
installed methodology -> .lifecycle/methodology/
code and deployed behavior -> target codebase source and runtime
```

Product records and Description files hold semantic authority entries. They may
govern future product judgment when admitted, current, and scoped.

Semantic authority entries should be cheap to retrieve. Entries use stable IDs,
state, scope, retrieval keys, target references when useful, related semantic
authority, and supersession so agents can load the smallest relevant semantic
authority slice instead of reading the whole product history.

Control records hold Clarity, Discovery, and Delivery process state, including
Context-pass state while Clarity is active and active product judgment while a
Delivery run is open. They can inform future work by explicit pointer, but
closed Control records do not govern future product judgment. Durable product
meaning must be written through the semantic authority update path or through
knowledge promotion.

Control records are process-local. A target may retain a closed process's
Control records in the commit that records that process, then remove current
`records/control/` contents before starting the next process. Current HEAD
should carry only Control records for the active process or neutral
Control-record scaffolding. Semantic authority and target artifacts preserve
cross-process product continuity.

Discipline holds installed package info and generated runtime material.
When a selected package shapes a pass, record the used material and effect in
the active Control record under `records/control/`.

Generated tooling support holds derived support for optional tools. Tool
findings, receipts, indexes, and prepared material become durable state only
when an agent records their interpreted effect in the owning durable record.

## Semantic Authority Record Folders

Product semantic authority entries live directly under `records/` by owning
surface, except Description:

```text
context/      product context, users, market, strategy, direction, and broad
              product-context atlas organization
intent/       intended behavior, acceptance meaning, and non-goals
assurance/    obligations, invariants, constraints, and required checks
blueprint/    structure, sequence, state, and dependency shape
```

Context may use product-area and cluster subfolders when a broad corpus needs a
Context atlas. Stable Context IDs remain semantic identity. Folder paths and
neutral `overview.md` files are retrieval and orientation affordances; current
Context entries own area overviews, canonical references, rationale leaves,
semantic neighborhoods, freshness policy, and promotion pressure.

Use Clarity when broad Context maintenance is the work. Context entries store
product meaning; Clarity Control records store source inventory, review checks,
retrieval proof, closure, and recommendations.

Description semantic authority files live beside the source files they
describe. Use `_main.go.desc.md` beside `main.go` for a one-to-one Description.
Use an appropriate `_name.desc.md` beside the owned source group for a group
Description.

## Control Record Folders

`records/control/` stores persisted Control records:

```text
discovery/maps/        Discovery plan maps
discovery/plans/       Discovery plan items
discovery/selections/  Discovery selection handoffs
delivery/work-boundaries/ Delivery Work Boundaries
delivery/evidence/     Evidence Packets and proof records
delivery/landings/     Landing Packets and handoffs
delivery/releases/     release summaries
delivery/promotions/   knowledge promotion decisions
delivery/archives/     archive decisions
delivery/closures/     closure records
```

## Overview Rule

Every folder under `records/` should have an `overview.md`.

Use [record-overview-files.md](record-overview-files.md) for neutral overview
contents. Do not create product meaning, plans, Work Boundaries, evidence, or
decisions during setup.
